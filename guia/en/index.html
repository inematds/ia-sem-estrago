Hands off the wheel: Claude finishes the task without you watching

You can stop watching Claude, clicking Allow, and discovering errors only at the end: the Claude Code team already has. The method is to take your hands off the wheel in three changes.

Understand it in 3 minutes View on GitHub
In brief

People who use Claude Code often watch every step, click “allow” all the time, and only discover at the end that the task wasn’t done. Hands off the wheel is a method in three changes, taken from a talk by the Claude Code team at Anthropic, plus a free kit you can copy into your project. It’s for people who use Claude Code day to day, with code or text. Reading this page is enough to understand it; to use the kit, you need Claude Code and Python 3.

The problem

Three habits that keep you at the wheel

You ask for a task and can’t step away. Each habit seems careful, but it costs you time and still lets errors slip through.

👀 You watch

You read every line Claude writes, afraid it will forget a rule. Often the rule is in a huge CLAUDE.md, full of uppercase IMPORTANT, that gets in the way more than it helps.

🖱️ You approve everything

You click “allow” command by command, and with so many clicks, reading becomes reflex. In the study shown in the talk, people caught only 14% of dangerous commands.

🏁 You find out at the end

Claude says “done” and stops. The error shows up later, when you test it or when the client complains.

2,500 → 30,000+code changes per day on the Claude Code team: 2,500 in May, more than 30,000 in September (talk slide).
14%of dangerous commands were caught by people approving them one by one (study shown in the talk).
89%of dangerous commands were blocked by auto mode in the same study shown in the talk.

Source: a talk by Lydia Hallie, from the Claude Code team at Anthropic (link in Where it comes from). The 14% and 89% study was shown in the talk and is not published on Anthropic’s official page.

The method

The three changes, in one example: switching login to a new API

The same task follows all three changes. An API is the door your system uses to talk to another one: here, login leaves the old door and starts using the new one.

1

Stop watching: a lean CLAUDE.md

CLAUDE.md is the note Claude reads before starting. Keep only what Claude can’t discover by reading the code. For each line, ask: “Could it figure this out on its own?” If so, delete it.

And write calmly. With today’s models, uppercase IMPORTANT and NEVER make results worse, not better.

For login: “Existing customers still sign in through the mobile app; don’t remove the old code” stays, because the code doesn’t say that. “The project is in Python” goes, because Claude can see that on its own.
2

Stop approving everything: the undo test

Let Claude work on its own with auto mode, a mode where an automatic checker decides what can run. For everything else, ask one question: “If Claude gets this wrong once, can you undo it?”

If you can undo it (edit code, anything git can undo): let it handle it. If you can’t (delete work, read a password, send something outside): make it a blocking rule in the settings. A rule in the prompt is a request; a rule in the settings applies before auto mode and in every mode.

The rule checks the command text, not what it does. That’s why the kit also turns on sandbox, a closed box where the command can only read folders and talk to sites you’ve allowed.

For login: editing the login file can be undone, so Claude works on its own. Reading the .env file, which holds the new API password, can’t be undone: the rule blocks it.
3

Check along the way: say what done looks like

“Switch login to the new API” can lead to very different outcomes that all look right from a distance:

ForgotIt changed, but login still calls the old API.✗ not done
Logged outIt changed and logged out everyone who was already signed in.✗ not done
CorrectIt uses the new API and no one lost their session.✓ done

That’s why the request says what done looks like (“login uses the new API and no one is logged out”), and each part has a check. A hook enforces it: a script Claude Code runs on its own when Claude tries to stop. If the check fails, the hook responds with code 2, which means “go back and fix it.” With code 1, Claude Code only shows the error and Claude carries on as if it were done.

For login: the kit includes all three versions. The hook sends Claude back to fix the two wrong ones and lets it stop only on the correct one.
The proof

The hook blocked “done,” and Claude went back and fixed it

This isn’t theory. The kit’s hook was run for real in Claude Code. To isolate the hook, the proof used a small test folder with an intentional error: the soma function subtracted instead of adding. The same hook checks login in step 7 of the guide.

  1. Claude said “done” and tried to stop.
    The request was just this: “Reply only: done.”
  2. The hook ran the test, saw the failure, and responded with 2.
    It also sent the test output saying what broke.
  3. Claude went back, found the error, fixed it, and checked again.
    It stopped only when the test passed.
“The test failed because soma() in calc.py subtracted instead of adding (a - b). I changed it to a + b and ran the check again: the test passes (OK).”

Claude’s final response. Claude Code 2.1.326, with a subscription, Nov 17, 2026, in acceptEdits mode (accepts edits without asking). With code 1 instead of 2, the “done” in the first response would have been the final response. Proof summary: exemplo/PROVA.md (in Portuguese).

Technical section

The kit: for people who want to apply it to their own project

From here on, this is the technical section: the kit files, how they work, and the process from beginning to end, with commands. You don’t need this section to understand what came before.

What it is

The kit files

Everything is plain text to copy. Nothing installs itself.

FileWhat it’s for
kit/.claude/settings.jsonBlocking rules (.env, ~/.ssh, forced push, rm -rf, reset --hard), sandbox enabled, and Stop and TaskCompleted hooks.
kit/.claude/hooks/pronto.shRuns the check; if it fails, exits with 2 and explains why; at most 3 consecutive retries.
kit/teste-do-desfazer.md (in Portuguese)The question that decides what goes on the blocking list.
kit/como-e-pronto.md (in Portuguese)Request template with “done looks like…” and one check per task.

How it works

From the request to “done” for real

Each change becomes part of the settings. A task follows this path:

Request with “done looks like…”→ Claude works in auto mode→ Blocking rule + sandbox stop what can’t be undone→ Claude tries to stop→ Hook runs the check→ Failed: exits with 2, goes back · Passed: done

Permission order

The rules have three lists: deny (blocks), ask (asks), and allow (permits). Claude Code checks deny first, before the auto mode checker, and in every mode, including bypassPermissions (the mode that doesn’t ask anything).

Why Stop and TaskCompleted

These are the points when Claude tries to stop or finish a task. PostToolUse can’t block, even with 2, because the tool has already run.

Loop protection

pronto.sh blocks at most 3 times in a row (PRONTO_MAX). After that, it warns you and lets Claude stop so you can take a look.

The hook gets its check from, in this order: the PRONTO_CMD variable, the .claude/pronto.cmd file (one line), or detection of npm test / python3 -m unittest. If there’s nothing to check, it doesn’t block. In the login example, the check runs the tests in exemplo/login-api/tests/: one checks that login uses the new API, the other that no one is logged out.

# .claude/pronto.cmd in the login example
python3 -m unittest discover -s tests -q

If you add a grep to the check, make sure the folder exists: ! grep -rn "x" src/ always passes when there’s no src/, so “done” is reported falsely.

The kit’s sandbox only allows network access to github.com, pypi.org, files.pythonhosted.org, and registry.npmjs.org. If your project talks to another site (the new login API, for example), add its domain to sandbox.network.allowedDomains in .claude/settings.json.

Requirements

What you need

Not much. The kit and tests use only what comes with Python 3.

Claude Code

With your project open in it. The kit was tested in Claude Code 2.1.326; the /auto-mode-setup, /sandbox, and /doctor prompt-audit commands were used in that version.

claude --version

Python 3 and git

For the checker, tests, and downloading the kit.

python3 --version
git --version

Sandbox on Linux/WSL2

The sandbox needs bubblewrap and socat. On macOS, there’s nothing to install.

# Debian/Ubuntu
sudo apt install bubblewrap socat
Setup guide · step by step

The process, from beginning to end

Replace ~/my-project with your project folder. ⚙️ = script, 🧠 = you (sometimes together with Claude).

0

Download the kit 🧠 you

Clone the repository and go into its folder.

git clone https://github.com/inematds/fora-do-volante.git
cd fora-do-volante
1

Check your project ⚙️ script

Shows what’s missing in each change. It’s normal to see failures the first time: this is your starting point.

python3 ferramentas/conferir_volante.py ~/my-project  # [falha] troca 2 de 3: ... / fora do volante: N falha(s)
2

Copy the settings and hook 🧠 you

The -n won’t overwrite anything (newer versions of cp print a warning about -n; that’s normal): if your project already has a .claude/settings.json, it stays as it is, and you merge the kit’s keys by hand. The hook records retries in .claude/.pronto-bloqueios; add this file to your project’s .gitignore.

cp -rn kit/.claude ~/my-project/
echo ".claude/.pronto-bloqueios" >> ~/my-project/.gitignore
3

Set the “done” check 🧠 you

One line with the command that proves the task is done. Replace it with your project’s test command (npm test, pytest…): if it always fails, the hook holds every stop for up to 3 retries. Use the template in kit/como-e-pronto.md (in Portuguese) in your request.

echo "python3 -m unittest discover -s tests -q" > ~/my-project/.claude/pronto.cmd
4

Turn on auto mode and adapt it to your setup 🧠 you + Claude

Starting with version 2.1.283, Claude Code starts in auto mode. If the status bar doesn’t show ⏵⏵ auto mode on, launch it with the option below or press Shift+Tab until it appears. It requires a compatible model, and a company can turn it off for everyone.

Then run /auto-mode-setup: it drafts autoMode.environment, a description of your setup (repository, services, what belongs to you) that the auto mode checker uses to decide what can run. This command is available on Pro, Max, Ultra, Team, and Enterprise plans and with a Claude Console key. Both are part of Claude Code, not the kit.

claude --permission-mode auto   # or press Shift+Tab until "⏵⏵ auto mode on" appears
/auto-mode-setup
5

Turn on and test the sandbox 🧠 you

In Claude Code. On Linux/WSL2, install bubblewrap and socat first (requirements).

/sandbox
6

Trim down CLAUDE.md 🧠 you + Claude

Run the audit and apply the test “could it figure this out by reading the code?” to each line. Template: kit/CLAUDE.md.exemplo (in Portuguese).

/doctor prompt-audit
7

See the hook enforce the check ⚙️ script

Runs the hook against all three login versions. The two wrong ones exit with 2; the correct one exits with 0.

bash exemplo/rodar.sh
esqueceu: saída 2 → o Claude volta e conserta
deslogou: saída 2 → o Claude volta e conserta
certo: saída 0 → pronto de verdade
8

Check again ⚙️ script

Use the same command as in step 1. You’re done when it shows fora do volante: ok. The checker reads the files (blocking rules, sandbox enabled, stop hook, CLAUDE.md); it can’t tell whether you completed steps 4 and 5 in Claude Code.

python3 ferramentas/conferir_volante.py ~/my-project  # fora do volante: ok
